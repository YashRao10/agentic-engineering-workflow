01 · The idea

Build it the way a real engineering team is built.

Software for aircraft is not written by one person. It is written by people with separate jobs, and checked by other people who report to someone else. This design copies that structure with agents, so the same checks and balances apply.

04 · Anatomy of one agent

Every agent runs the same loop.

Pull the input, draft, check it, ask a person, write it down, tell the Orchestrator. If the person asks for changes, the loop goes around again with their words attached.

  1. 01The agent pulls its input from the record. It never gets a handoff payload from another agent.
  2. 02It drafts with a model. A person chooses cloud or local for the whole run.
  3. 03It checks its own draft for missing coverage and copied text, and redrafts before anyone sees it.
  4. 04A person reads the draft. They can approve, or type what to change and send it back around the loop.
  5. 05Only after approval does the draft go to the record. The write is recorded with who approved it.
  6. 06The agent tells the Orchestrator it finished. The note is a pointer to the record.
  7. 07The Orchestrator releases the next agent, which reads what was just written.
00 · Where the model runs

The model runs where the project allows it.

The planner picks cloud or local once, for the whole run. For restricted work the choice is made for you, and the code enforces it instead of a policy document.

This project is

☁

Cloud model

  • Stronger and faster
  • Data leaves the machine
  • Good for open projects
▣

Local model

  • Everything stays on the machine
  • Smaller, so jobs are kept narrow
  • Required for restricted work
  • Checked before the run: reachable, installed, loaded
  • Restricted runs: the operating system blocks everything except this machine
05 · The firewall

The team that builds it cannot talk to the team that checks it.

In a real project, QA is not supposed to be friends with the person whose work they are auditing. The code enforces that. Try breaking it.

Two walls, not one

Wall one is in the code: the teams cannot message each other or read each other's areas. Wall two is the operating system: the audit runs as its own process on a read-only copy of the record, with writes allowed only in its own folder and the network switched off. When it finishes, the real record is checked byte for byte. If anything changed, the audit is thrown away.

07 · Do the tests actually work?

A passing test proves nothing until you break the code on purpose.

The verification agent makes small deliberate defects in a copy of the code, then checks whether the tests notice. Any defect the tests miss goes back to the test agent with the exact line. The counts here are illustrative.

int gear_warning(int alt_ft, int gear_down) {
    if (alt_ft < 500 && !gear_down) {
        return 1;   /* warn */
    }
    return 0;
}

One mutation: change < to <=. A good test set fails at exactly 500 feet. A weak one never tries that value and the bug survives.

00 · When the audit fails

A finding goes back to the agent that owns it.

Compliance never talks to development. A launcher, either a person or the run script, reads the findings and sends each one to the agent that wrote the item. Everything downstream of that agent reruns.

08 · Getting it into the platform

Publishing happens once, so every guard sits in front of it.

The certification platform has no update and no delete. Whatever is written stays written. So nothing goes in during the run. It goes in at the end, after the audit, and only if a person says yes.

// one call per item, sent only after the audit gate opens create_hlr({ item: "GEAR-DEMO", id: "HLR-1", text: "Warn below the limit, gear not down", traces_to: ["SR-1"] }) // response { ok: true, id: "item_0192" }
01One call per itemEvery requirement, design item, test and procedure is its own small call, so each one is easy to log and to check.
02A ledger stops duplicatesNothing can be deleted, so every call is recorded. A retry skips what already went in, and an unreadable response is marked unknown instead of being sent twice.
03Then read it all backThe same read tools pull the records out and compare them with what was sent. A mismatch is reported, not hidden.

10 · What building it taught me

Six things I would tell the next team.

01

A model should not grade its own work

The compliance team uses plain rules instead of a model. The same kind of mistake does not get checked by the same kind of mind.

02

Passing the audit is not the same as being good

The audit says the record is complete and traceable. Whether the requirements are right is a person's call, which is why the gate exists.

03

Pass pointers, not payloads

Agents hand off a note that says where the work is. The next agent reads the record, so there is one source of truth.

04

Design around what the platform cannot do

No update, no delete, and no document content writes. That one fact decided when and how publishing happens.

05

Test the checkers too

I broke the record on purpose, missing tests, orphaned links, stale downstream items, and confirmed the audit caught each one.

06

Small models need small jobs

Asking a small local model for one narrow addition and merging it in code beat asking it to rewrite everything.

What is not proven yet

  • The full flow has run on sample briefs with a cloud model. The local-model path for restricted work still needs its own run.
  • The agents' output is only as good as the requirements a person approves.
  • Records written to the platform cannot be edited later, so rework has to finish before publishing.
00 · Plain-language glossary

The words on this page, in plain English.

DO-178C

The standard that governs software in airborne systems. It asks for proof at every step: what the software must do, how it is built, and how it was tested.

High-level requirement

A statement of what the system must do, written so it can be tested. One per behavior in the customer brief.

Low-level requirement

A finer-grained statement of how a piece of the software will meet a high-level one. The code is written against these.

Traceability

An unbroken chain from a requirement, to its design, to its code, to the test that proves it. A gap anywhere is a finding.

MCP

Model Context Protocol, a standard way for an AI agent to use another system's tools. Here it is how agents read from and write to the platform.

Orchestrator

The plain-code controller that releases each agent when the one before it finishes. It uses no AI, so it behaves the same way every time.

Firewall

The rule that development and compliance never message each other. Only the shared record connects them, so QA stays independent.

Mutation check

Deliberately breaking a copy of the code to see whether the tests notice. A test that passes both ways is not proving anything.

Provenance

The record of who approved each item, which model drafted it, and when. It makes any auto-approval visible to the auditor.

00 · Where it stands

What is done, and what is next.

Done

  • Seven development agents and three compliance agents, run by a plain-code Orchestrator.
  • Human gate at each agent, with feedback that reaches the redraft.
  • Firewall between the teams, enforced in code and again by the operating system, so the audit cannot change the record it is checking.
  • Audit gate, content fingerprint, stale-record check, and guarded publish with read-back.
  • A publishing step that only runs after a clean audit: a document agent renders the design description and test report straight from the audited record (no model, so the documents cannot drift from it), and an importer writes and reads back.
  • A test-strength check that can be switched from a warning to a hard stop, so a weak test set blocks the audit.
  • Each development agent now sends back its own draft when links are missing or an id repeats, before a person has to look at it.
  • A regression suite that runs without calling a model.
  • Local-model safeguards: a readiness check that stops a run at once instead of quietly degrading, smaller jobs per call, per-agent model choice under the same restricted-work rules, a repair step that shows a model its own rejected code, a fixed memory window so long prompts are not silently cut, and a watchdog that only stops a run that has gone quiet.
  • A first small slice written to a sandbox project and read back clean.

Proven so far

  • Full runs on invented sample briefs, with a cloud model.
  • Generated code builds and its tests pass.
  • The audit catches deliberately broken records.
  • A full end to end run on a second operating system (Windows, through WSL): audit ready, 8 of 8 requirements traced, 24 of 24 planted defects caught, publish gate held for a person.

Passing the audit means complete and traceable, not that the requirements are right. That judgment stays with the person at the gate.

Next

  • A full run on a local model for restricted work, using the new safeguards (built and tested with stand-in models, not yet proven on a real local run).
  • A full publish to a sandbox project, then read back.
  • Attach the generated documents to the platform by hand, since it cannot accept document content yet.
  • A trial on a real, non-sensitive project with an engineer reviewing every gate.
